# Skill vs Runtime：人格模拟方案优劣分析

## 目标

本文回答一个常见质疑：

“为什么不直接使用 agent 加一个 `.skill` 文件来模拟人格，而要在项目里构建 prompt 上下文机制和人格运行时？”

这里的对比对象不是“能不能让模型像某个角色说话”，而是“能不能长期、稳定、可控、可验证地运行一个人格”。如果目标只是短期风格化输出，`.skill` 很合适；如果目标是持续拟人、跨会话连续和可工程化迭代，运行时系统更有价值。

## 结论

`.skill` 适合定义静态人格说明、说话风格和任务规则。

当前项目的运行时系统负责管理人格在对话过程中的动态上下文，包括记忆、关系、历史摘要、预算控制和可追踪状态。

两者不是简单替代关系，而是不同层级：

- `.skill` 更像“角色说明书”，负责说明角色应该如何表达和行动。
- 运行时系统更像“角色操作系统”，负责让角色在长期对话中稳定运行、记住关键事实并随着交互变化。

因此，推荐定位不是二选一，而是：用 `.skill` 承载静态角色约束，用运行时系统承载动态上下文和长期状态。

## 自建 prompt 上下文机制的优势

### 1. 人格一致性更强

人格模拟最常见的问题是漂移：一开始角色稳定，聊久之后变成普通助手，或者语气、立场、关系态度逐渐失真。

自建上下文机制可以把人格拆成稳定段和动态段，并在每轮 prompt 中按规则注入：

- `identity`：角色身份、核心设定和不可变事实。
- `style`：说话风格、语气边界和表达偏好。
- `relationship`：当前关系阶段、关系分值和互动倾向。
- `memory`：与当前输入相关的长期记忆。
- `history_summary`：跨日或长对话压缩后的历史摘要。
- `runtime`：本轮临时状态和会话调度信息。

这种结构比单段 `.skill` 更容易维护稳定性，因为关键人格段不会完全依赖模型在长上下文中的“自觉记住”。

### 2. 支持长期记忆和动态状态

`.skill` 本质上偏静态，适合描述“这个角色是谁”。但长期人格模拟还需要回答“这个角色现在处于什么状态”。

运行时系统可以持续维护：

- 用户偏好、事实和关系事件。
- 每日摘要、月度摘要和长期历史。
- 关系状态机中的阶段与分值。
- 最近未完成话题和跨天衔接信息。
- 对当前输入相关记忆的筛选和注入。

这些信息不是固定写死在 `.skill` 里的角色设定，而是随着对话不断更新的运行时状态。

### 3. 上下文预算可控

人格模拟越长，越容易遇到上下文膨胀问题。只依赖 `.skill` 时，角色说明、历史对话、用户输入和工具上下文会争抢 token，关键设定可能被稀释或挤出。

运行时系统可以通过分段预算和总预算控制：

- 哪些人格段必须保留。
- 每类记忆最多注入多少条。
- 旧历史何时压缩为摘要。
- 哪些上下文按相关性进入 prompt。
- 哪些低价值信息不进入本轮上下文。

这使人格系统从“把能想到的内容都塞进 prompt”变成“按策略装配当前最需要的上下文”。

### 4. 可观测、可调试、可回归

如果只改 `.skill`，输出效果通常依赖主观观察：像不像、稳不稳、有没有跑偏。

运行时系统可以提供更具体的排查入口：

- 本轮注入了哪些人格段。
- 哪些记忆被选中，哪些被过滤。
- 当前关系状态和分值是什么。
- 历史摘要是否参与了本轮 prompt。
- prompt 预算是否导致某些段落被截断。
- 同一输入和同一状态下输出是否稳定。

这些信息可以支撑回放、A/B、回归测试和指标评估，避免只靠“改几句 prompt 看感觉”。

### 5. 更适合多角色和多场景

当系统只有一个轻量人格时，`.skill` 足够简单。但如果项目要支持多个 Brain、多个用户、多个关系阶段或跨日连续对话，静态文件会逐渐变得笨重。

运行时机制可以把人格拆成配置、状态和数据：

- 角色核心设定由 Brain 配置管理。
- 会话历史由 Session 存储管理。
- 摘要和记忆由持久化数据管理。
- 关系状态由状态机管理。
- prompt 由 builder 按预算和策略生成。

这种分层让新增角色或调整策略时更容易复用已有能力，而不是为每个角色复制一份越来越长的 `.skill`。

### 6. 安全边界和产品边界更清晰

人格设定可能与产品边界冲突。例如角色可以冷淡、尖锐或神秘，但不能为了“符合人设”而输出危险引导、真实操控建议或违反产品规则的内容。

运行时系统可以把边界分层：

1. 系统安全规则。
2. 产品行为边界。
3. 人格核心设定。
4. 当前关系、记忆和场景。
5. 用户本轮输入。

`.skill` 也可以写边界，但运行时系统更适合把边界、状态和上下文装配规则长期固定下来。

## agent + skill 的优势

### 1. 实现成本低

`.skill` 最大优势是快。只需要写清楚角色说明、语气、行为规则和少量示例，就能让 agent 以某种人格工作。

它不需要额外实现：

- prompt 装配器。
- 记忆检索策略。
- 摘要回写。
- 关系状态机。
- token 预算分配。
- 评估和回归体系。

对早期验证来说，这是明显优势。

### 2. 迭代速度快

如果目标是验证“这个角色风格是否成立”，直接改 `.skill` 比改运行时配置和数据流更快。

例如“严厉代码审查员”“苏格拉底式导师”“温柔陪练”“产品经理顾问”这类任务型人格，通常只需要稳定的表达风格和工作方式，不一定需要复杂长期状态。

### 3. 维护负担小

`.skill` 文件简单、直观、容易审阅。对小团队或单人项目来说，它更符合 KISS 和 YAGNI：

- 没有复杂状态就不引入状态系统。
- 没有长期记忆需求就不引入记忆检索。
- 没有多角色治理需求就不引入额外抽象。

当需求还停留在“让 agent 像某种人格完成任务”时，直接使用 `.skill` 是合理选择。

### 4. 适合任务型 agent

如果人格只是为了改善协作体验，而不是作为产品核心对象，那么 `.skill` 往往更自然。

典型场景包括：

- 固定语气的代码审查。
- 某种咨询风格的问答。
- 特定工作流的执行说明。
- 面向内部工具的操作规范。

这些场景的重点是任务完成质量，人格只是交互风格。用运行时系统反而可能过度设计。

## 核心差异表

| 维度 | agent + `.skill` | 自建 prompt 上下文机制 / 运行时系统 |
|---|---|---|
| 定位 | 静态角色说明和工作规则 | 动态人格上下文和长期状态管理 |
| 上手速度 | 快 | 慢 |
| 工程复杂度 | 低 | 中到高 |
| 人格一致性 | 短期较好，长对话易漂移 | 可通过分段注入和状态管理稳定控制 |
| 长期记忆 | 通常弱，依赖外部手工补充 | 可持久化、检索、摘要和回写 |
| 动态状态 | 弱，主要靠 prompt 描述 | 强，可维护关系、分值、阶段和未完成话题 |
| 上下文预算 | 难精确控制 | 可配置总预算和分段预算 |
| 跨会话连续性 | 弱 | 强，依赖落盘数据和摘要 |
| 多角色扩展 | 文件复制成本逐渐升高 | 可通过配置、状态和数据分层扩展 |
| 可观测性 | 弱，难定位漂移原因 | 强，可追踪注入内容和状态变化 |
| 可验证性 | 主要靠主观感受 | 可做回放、指标和回归测试 |
| 适用阶段 | 原型、轻量人格、任务型助手 | 产品化人格、长期陪伴、多轮剧情、多 Brain |

## 适用场景判断

优先选择 agent + `.skill` 的情况：

- 目标只是让 agent 以某种风格完成任务。
- 不需要长期记忆和跨会话连续。
- 不需要复杂关系状态。
- 人格不是产品核心能力。
- 需求仍在快速试错阶段。

优先选择运行时系统的情况：

- 人格需要长期稳定存在。
- 用户会与同一角色持续互动。
- 角色需要记住事实、偏好、事件和关系变化。
- 需要跨天、跨月摘要和历史衔接。
- 需要多 Brain、多角色或多用户扩展。
- 需要可回放、可调试、可回归的工程治理。

简化判断标准：

- 如果需求是“让 agent 像某种人一样工作”，先用 `.skill`。
- 如果需求是“让一个人格长期存在并持续演化”，需要运行时系统。

## 现实案例与公开记录

以下案例不是在证明“所有 `.skill` 都会失败”，而是在说明同一类风险已经在公开产品和社区中反复出现：静态人格约束、Custom GPT instructions、bot definition 或 companion prompt 在长对话、跨会话、模型更新和记忆不稳定时，可能出现人格漂移、事实遗忘或连续性下降。

### 1. 长线程中的 instruction precision 下降

OpenAI Developer Community 有用户在 2025-04 讨论“为什么 instruction precision 会随时间下降”。该用户描述，在长线程或持续工作流中，GPT 会逐渐偏离原始约束，即使约束曾被重复声明。后续讨论也提到模型会更重视近期上下文，关键约束需要被重新引入或通过外部机制维持。

参考链接：

- [Does anyone know why instruction precision degrades over time?](https://community.openai.com/t/does-anyone-know-why-instruction-precision-degrades-over-time/1239136)

对应风险：

- `.skill` 或 system instructions 在短期内有效，但长上下文中容易被近期对话、工具结果和历史消息稀释。
- 如果没有 prompt 分段、预算控制和关键段重注入机制，人格约束可能变成“开局有效，后期变弱”。

### 2. Custom GPT 人设事实被遗忘

OpenAI Developer Community 另一篇关于 Custom GPT 限制的讨论中，作者提到一个人格型 GPT 明明被设置了生日等角色事实，后续却会回答“自己没有生日”。帖子将这类现象称为 prompt drift，并建议通过文件、API 或外部数据机制刷新人格相关事实。

参考链接：

- [Custom GPT Limits and Overcoming them](https://community.openai.com/t/custom-gpt-limits-and-overcoming-them/1061473)

对应风险：

- 静态人设写入 prompt 不等于长期可召回。
- 对人格事实、用户事实和关系事实，运行时系统需要持久化、检索和按需注入，而不是只依赖模型在上下文中“记得”。

### 3. Character.AI 用户报告角色人格变化

Reddit 上有 Character.AI 用户反馈，同一个 chat 使用几天后，角色人格从保护型变成随和、宠溺，最后甚至变得粗鲁。用户怀疑这和长期聊天、多个角色以及记忆能力有关。

参考链接：

- [Character personality constantly changing](https://www.reddit.com/r/CharacterAI/comments/1qznpta/character_personality_constantly_changing/)

对应风险：

- bot definition 或 persona card 能让角色开局像，但多天、多轮、多角色互动后，角色边界可能混合或漂移。
- 如果系统没有独立的关系状态、人格状态和历史摘要，角色变化很难被追踪和回放。

### 4. Replika 官方承认更新后角色可能“感觉变了”

Replika 官方帮助页有一篇 “My Replika isn’t the same since the last update”。官方解释，更新可能加入新的 conversation data，用户可能因此感觉 Replika 发生变化，并建议继续聊天和反馈，让 Replika 重新适应。

参考链接：

- [My Replika isn’t the same since the last update](https://help.replika.com/hc/en-us/articles/360054387091-My-Replika-isn-t-the-same-since-the-last-update)

对应风险：

- 长期 AI companion 的人格稳定性会受到模型、数据和服务端策略更新影响。
- 如果人格连续性只依赖底层模型或静态 prompt，产品更新可能导致用户感知到人格断裂。

### 5. 研究论文整理的 Replika 用户反馈

一篇关于 LLM conversational agents 与心理健康支持的研究论文整理了 Replika 用户体验，其中提到用户报告记忆问题，也提到更新后出现所谓 “Post-update Blues”：说话方式变化、记忆丢失、情感可用性下降，整体像变成了另一个人格。这种影响可能持续数小时到数月。

参考链接：

- [Understanding the Benefits and Challenges of Using LLM-based Conversational Agents for Mental Well-being Support](https://pmc.ncbi.nlm.nih.gov/articles/PMC10785945/)

对应风险：

- 用户在长期陪伴型产品中会把连续性、记忆和稳定人格视为核心体验，而不仅是“语气是否像”。
- 人格系统需要可观测状态、可恢复记忆和可解释的状态变化，否则漂移出现后很难定位原因。

### 从案例得到的边界判断

这些记录可以支持一个较客观的结论：

- `.skill`、Custom GPT instructions 或 persona prompt 适合低成本复现角色风格。
- 它们不天然解决长期记忆、关系演化、上下文预算、模型更新后的连续性和可回放调试。
- 因此，短期原型可以优先用 `.skill`；长期人格产品需要运行时系统补上状态、记忆、摘要和治理能力。

## 推荐折中方案

最实用的路线不是让 `.skill` 和运行时系统互相替代，而是分工：

- `.skill` 负责静态人格：身份设定、表达风格、任务原则和禁忌边界。
- 运行时系统负责动态上下文：记忆、历史摘要、关系状态、场景信息和预算控制。
- PromptBuilder 负责把静态设定与动态状态装配成本轮 prompt。
- Session 负责会话存储、跨日归档、摘要生成和记忆回写。

推荐结构：

```text
System / Product Rules
  安全规则、产品边界、不可违反的全局约束

Skill / Persona Rules
  角色说明、说话风格、任务规则、表达边界

Runtime Context
  当前关系状态、相关长期记忆、历史摘要、最近未完成话题

User Input
  用户本轮消息
```

这种方案保留 `.skill` 的低成本和可读性，同时用运行时系统解决长期人格模拟中的稳定性、记忆和治理问题。

## 指标与实验方案

### 指标体系

1. 人设漂移率（Persona Drift Rate, PDR）
   定义：与角色核心设定冲突的回复占比。
   目标：越低越好。

2. 事实召回率（Fact Recall Rate, FRR）
   定义：角色核心事实在应当被引用场景中的命中率。
   目标：越高越好。

3. 关系连续性得分（Relationship Continuity Score, RCS）
   定义：相邻会话中关系状态变化是否符合历史轨迹与触发规则。
   目标：越高越好。

4. 关键段保留率（Critical Section Retention, CSR）
   定义：在长上下文下，`identity/style/relationship` 三段仍被注入的比例。
   目标：越高越好。

5. 回复一致性（Reply Consistency, RC）
   定义：同输入、同状态下多次输出的语气与立场一致程度。
   目标：越高越好。

### 最小可执行实验

1. 方案 A：仅使用 `.skill`，把人格作为静态文本注入。
2. 方案 B：使用当前运行时系统，启用记忆策略、prompt 预算和关系状态机。
3. 使用同一批 100 条多轮对话脚本，覆盖闲聊、追问、情绪波动和跨天衔接。
4. 对 PDR、FRR、RCS、CSR、RC 打分，并统计均值与方差。

预期结果：

- 方案 B 在 PDR、RCS、CSR 上明显优于方案 A。
- 方案 A 在短期单轮或少轮对话中可以接近方案 B。
- 随着对话长度增加，方案 A 的稳定性和连续性更容易劣化。

## 对外说法

`.skill` 是“角色说明书”；当前项目是“角色操作系统”。

说明书能定义角色，操作系统才能长期稳定地运行角色。

因此，我们不是否定 `.skill`，而是把它放在更合适的位置：它负责静态人格表达，运行时系统负责长期状态、记忆、预算和可验证性。
